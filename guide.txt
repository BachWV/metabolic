metabolic
=========
Standalone Rust/Axum + SQLite blog comments, with an admin page and a vanilla
JavaScript/CSS component. Includes threaded replies, moderation, CSRF protection,
rate limiting, durable SMTP notification jobs, migration and database backups.

Build and verify
----------------
cargo fmt --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo build --release --locked

Configuration
-------------
Copy examples/config.example.yaml into private/config.yaml (ignored by Git).
Create the private directory first. Restrict access to the local configuration.
Run `metabolic hash-password` interactively and put its output in password_hash.
The example deliberately contains an invalid placeholder, never a usable password.
Set site_url, origins and SMTP fields for your own deployment only in that private
file. No real deployment configuration is included in this repository.

metabolic serve --config private/config.yaml
metabolic import private/export.json --mapping private/mapping.json --config private/config.yaml
metabolic backup private/backup.sqlite3 --config private/config.yaml
metabolic retry-mail --config private/config.yaml
metabolic preflight private/export.json --public-dir public
metabolic hash-password

All service/database commands require a complete, valid YAML configuration.
There is no implicit configuration search, environment configuration, variable
expansion or --database override. Even RUST_LOG is not read; logging is fixed to
INFO. CLI arguments select an operation and its input/output files only.
The database path is relative to the YAML file's directory, not the shell's
working directory. Other CLI paths are relative to the shell's working directory.
The database parent directory must already exist. Backup refuses to overwrite an
existing destination; retry-mail requires an existing database. Import creates
its database if necessary and does not send notifications for imported comments.
Preflight and hash-password do not read configuration. Preflight prints a JSON
report containing the mapping object; save/edit that mapping object separately
for import. Unknown, duplicated or mistyped YAML keys are rejected. YAML parsing
errors report location without echoing potentially secret configuration values.

Required keys: bind (numeric IP:port), database, origins (nonempty exact HTTP(S)
origins without trailing slash), site_url, password_hash, cookie_secure,
proxy_mode (direct/nginx/cloudflare).
Optional SMTP keys: smtp_host (empty disables delivery), smtp_port (default 587),
smtp_user, smtp_password, mail_from, mail_to. A configured host requires valid
sender/recipient mailboxes and nonempty credentials. Port 465 uses implicit TLS;
other ports use STARTTLS. Disabled delivery retains queued notifications.
Keep cookie_secure true with HTTPS. For local HTTP testing only, set it false.
Include the admin service origin as well as the blog origin in origins.
Admin UI: /admin. Liveness/database check: /healthz.

Proxy modes
-----------
direct: use the actual TCP peer; ignore forwarded visitor headers.
nginx: trust X-Real-IP only from loopback peers. The local reverse proxy must
replace this header with the actual visitor IP; never forward arbitrary input.
cloudflare: requires a loopback bind and a local cloudflared process in the same
network namespace. Accept only one valid CF-Connecting-IP (IPv4 or IPv6), require
a loopback peer, and never fall back to X-Real-IP or X-Forwarded-For. Restrict local
access appropriately; other local processes are inside this trust boundary.

Component and embedding
-----------------------
component/comments.js and component/comments.css have no Hugo dependency.
examples/embed.html is a complete HTML example. Serve the repository using a
static HTTP server (do not open through file://), set data-api to the service
origin and data-page to a stable site-relative article path, and add the example
page's HTTP origin to YAML origins. Each page supports one #blog-comments element.
Copy the example's section markup plus stylesheet/script tags into any site.
All public API calls omit credentials; admin UI is served by the backend itself.

Hugo integration
----------------
Copy component/comments.js to static/js/comments.js and component/comments.css
to static/css/comments.css in the consuming blog. Copy examples/hugo/comments.html
to layouts/partials/comments.html, then include {{ partial "comments.html" . }}
from the article footer. Configure the consuming blog's config.toml as follows:

[params.comments]
enabled = true
apiURL = "https://comments.example"

These are frontend embed settings; the metabolic backend reads YAML only.
The originating blog already has these three files and its footer/config hookup.
Extraction preserves that existing integration, old backend, running service and
database. No service switch or data migration is performed by this repository.
To update the component later, copy the files above from this repository to the
blog and rebuild the blog. Do not remove its footer include or frontend settings.

Repository hygiene
------------------
No source Git history, original deployment scripts or uppercase-named Markdown
files are carried over. Local settings, exports, databases, backups, logs and
build outputs stay ignored. Only the fictional YAML example is tracked. Review
staged contents before every commit; Git ignore rules are not a secret scanner.
